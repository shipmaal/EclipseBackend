# Lunar limb profile — design and implementation plan

Status: **PRs 1 (data + profile) and 2 (local contacts) done** — §9 has
their results. PRs 3–4 are open, plus observer elevation (§8). Companion to `CODE_REVIEW_FOLLOWUPS.md`
§6, which removed the other known model errors and left the mean lunar limb as
the largest one. Everything in `CLAUDE.md` applies: cite every formula, both
languages in the same PR, fixtures regenerated by `tools/dump_oracle.py`,
known discrepancies are strict xfails.

## 1. Problem

Today the Moon is a sphere. The umbral cone uses the reduced radius
`K_UMBRA = 0.2722810` (1736.65 km) and the penumbral cone
`K_PENUMBRA = 0.2725076` (1738.09 km) [Espenak]. `K_UMBRA` is Espenak's
allowance for the *mean* depth of the limb valleys. The real limb departs from
a sphere by about ±3″ (±6 km), which moves [NASA-limb]:

| quantity | size of the limb effect |
| --- | --- |
| C2 / C3 contact times, central duration | ~1–3 s |
| umbral path limits | ~1–3 km north/south |
| location of greatest duration | ~10–20 km |
| C1 / C4, magnitude, obscuration | ≲ 0.5 s, ≲ 1e-3 (not in scope, §7) |

Watts-chart profiles gave ~0.5 s; LRO/Kaguya-based profiles give ~0.2 s
[NASA-limb]. With W1/W2 done, our mean-limb durations sit within ±0.4 s of
Espenak's mean-limb values. The limb is now the largest error against what an
observer actually sees.

**Correction to an earlier claim.** The 2021-12-04 width residual (−0.86 km
against Espenak, §6) is **not** explained by the limb profile: Espenak's
published width is itself a mean-limb (`k2`) number, so both sides share the
approximation. That residual stays open on its own. The limb profile changes
what we compare against (limb-corrected sources, §5), not that comparison.

## 2. Data source — LRO LOLA gridded DEM (recommended)

| | LRO LOLA `LDEM_*` (PDS) | Kaguya LALT | Watts charts |
| --- | --- | --- | --- |
| origin | NASA LRO, Lunar Orbiter Laser Altimeter [LOLA] | JAXA SELENE | USNO photographic, 1950s |
| licence | NASA / PDS, public domain | JAXA data policy (attribution/terms) | historical, digitised copies vary |
| heights relative to | Moon **centre of mass**, sphere 1737.4 km | CoM | "Watts datum" (needs CoF offset corrections) |
| frame | Mean Earth/Polar Axis of DE421 | own | own |
| verdict | **use** | fallback only | no |

Products (checked on `pds-geosciences.wustl.edu`,
`lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/cylindrical/img/`), all int16
little-endian, `radius_m = DN × 0.5 + 1737400`:

| product | pixels/deg | pixel at equator | size |
| --- | --- | --- | --- |
| `LDEM_4` | 4 | 7.6 km | 2.1 MB |
| `LDEM_16` | 16 | 1.9 km | 33 MB |
| `LDEM_64` | 64 | 0.47 km | 531 MB |
| `LDEM_128` | 128 | 0.24 km | 2.1 GB |

Why LOLA: heights are referenced to the centre of mass, which is also what the
DE ephemeris gives. So no Watts-datum or centre-of-figure correction is
needed. Public domain means no licence text to carry. Its frame is directly
available in SPICE (below).

**Resolution.** PR 1 ships `LDEM_16`, which is the size of a kernel. It also
measured the C2/C3 change from `LDEM_16` to `LDEM_64` on the 2017 and 2024
paths (§9.1). The change is 0.1–0.2 s typically and up to 0.5 s near the
edge, above the 0.1 s threshold set here. But the `LDEM_64` band is ~200 MB
and costs ~12× more per profile, so the switch is an open decision (§8).
Nothing in the code assumes 16 pixels/degree: the band file carries its grid.

**Lunar orientation.** The DEM is in `MOON_ME` (DE421 mean-Earth). NAIF
provides it for DE440 as `MOON_ME_DE440_ME421`, defined in
`fk/satellites/moon_de440_250416.tf` on top of the binary PCK
`pck/moon_pa_de440_200625.bpc`. `kernels.bootstrap` adds both to
`eclipse.tm`. The `mirror` source takes the same two files, unmodified, from
this repository's `limb-data` branch. `IAU_MOON` (text PCK only) still works as
`moon_frame`: it differs from `MOON_ME` by 0.001° here and moves the profile by
≤ 16 m (§9.3).

**Distribution.** The DEM is treated like a kernel: gitignored, fetched by
`kernels.bootstrap --limb`, and SHA-256-pinned.
- From NAIF/PDS, bootstrap downloads `LDEM_16` and cuts the limb band locally
  with `kernels/limb_band.py`.
- The `mirror` source downloads the same bytes, pre-cut
  (`lola_ldem16_limb20.bin`, 16 MB), from the data-only `limb-data` branch at
  a pinned commit on `raw.githubusercontent.com`.

The cut is deterministic, so both routes must produce the pinned SHA-256.
Baking it into the Docker image waits until the API uses it (PR 2). If the
band is absent, `limb=profile` will answer 503, as missing kernels do today.

## 3. Method

### 3.1 The key simplification — one profile per instant, not per observer

An observer inside or near the umbra sees the Moon's centre along the shadow
axis to within D/Δ ≈ 150 km / 380 000 km ≈ 0.02°. That changes the visible
limb by far less than the DEM resolution.

So for everything umbral (C2/C3, durations, umbral limits), **the limb profile
depends only on time.** It is the silhouette of the DEM seen along the shadow
axis ẑ of the fundamental plane [ES92] 8.32, expressed in that plane's own x̂
(east), ŷ (north) axes. The same frame avoids any sky-mirror or
position-angle convention.

In the Moon's body frame, the Sun–Moon line turns at 360°/synodic month =
0.51°/h. That moves the viewed limb by ~1.5° over a three-hour path. The
profile is therefore a function of time and is not constant over an eclipse.

(For C1/C4 the observer is up to one Earth radius off-axis, which is ~1° of
topocentric libration. That is one reason C1/C4 are out of scope, §7.)

### 3.2 Computing a profile ρ(ψ, t)

1. At epoch t, rotate x̂, ŷ, ẑ into `MOON_ME` using SPICE `pxform`. This is
   at the Moon's light-time-corrected epoch, consistent with the `LT+S`
   positions in `ephemeris.py`.
2. The band file holds every DEM pixel within 20° of the mean limb, the great
   circle ⟂ +x of `MOON_ME`: |n·x̂_ME| ≤ sin 20°.
   - A peak of height h lying α beyond the limb shows over it only if
     cos α > R/(R+h); for h = 10 km that means α < 6.2°. We allow 8°.
   - At eclipses the view axis stays within 6.65° of −x̂_ME (§9.4).
   - So 12° of axis tilt is covered. `silhouette` refuses a view outside it
     rather than return a truncated profile.
3. Project each point p = r n (CoM-centred, km, r = 1737.4 + DN·0.0005) onto
   the plane: q = (p·x̂, p·ŷ). Its polar angle is ψ = atan2(q_y, q_x).
   Its apparent radius is **perspective**: the observer is at distance D
   along −ẑ, so the radius is |q| / (1 + w/D) with w = p·ẑ, in km at
   distance D. PR 2 found this matters (§9.6). A peak in front of the limb
   plane looks taller by R² sin α / D, up to ~0.9 km at α = 6°. The
   orthographic projection of PR 1 was 0.2–0.6 s off the 3D oracle.
   - D is the Moon's distance from the fundamental plane (`limb_axes`,
     the element z in km).
   - The observer's own ζ (≤ 1 Earth radius, 1.7 % of D) is ignored. That
     is ≲ 10 m for typical silhouette points.
   - Points with radius ≤ R_ref − 20 km cannot be on the silhouette and
     are dropped.
4. ρ(ψ) = the largest |q| in each bin of Δψ = 0.05° (≈ 1.5 km along the
   limb). Two things feed each bin:
   - the DEM points in it;
   - every grid edge between two retained points (east and south
     neighbours) where it crosses a bin boundary, its radius linear in ψ
     between the end points.

   The edges are needed because `LDEM_16` samples the limb every ~1.9 km,
   coarser than a bin. With points alone, some bins hold only points from
   behind the limb, which creates false valleys up to 18 km deep on a
   synthetic sphere (§9.2). With edges, the profile is the silhouette of
   the piecewise-linear surface. Any bin still empty is filled by periodic
   linear interpolation (more than 10 % empty is an error). Values between
   bin centres are linearly interpolated. Store δρ(ψ) = ρ(ψ) − ρ_sphere(D).
   Here ρ_sphere = R/√(1 − (R/D)²) is the LOLA sphere's own apparent
   radius, its tangent cone, which is what the cone elements' k describe.
   A smooth sphere therefore gives δρ = 0 at any D.

Cost is 8 M band points per profile for `LDEM_16`: 70 ms native (4 threads,
180 ms on one) and ~4 s for the Python oracle. Per model, profiles are to be
cached on a time lattice (Δt = 5 min) and linearly interpolated in t. The
interpolation error against an exact profile is ≤ 22 m (§9.3).

### 3.3 Contact function in fundamental-plane units

All quantities are at the observer's plane, in Earth equatorial radii, from
the existing elements [ES92] 8.33 / [MeeusSE]. Let P = (ξ − x, η − y) be the
observer's offset from the shadow axis. The Moon's and Sun's apparent radii,
scaled to the plane, follow from the cone radii (the identities `_obscuration`
already uses for the radius ratio):

    R_m = (L1' − L2') / 2        R_s = (L1' + L2') / 2

Those two are evaluated with *one* lunar radius, k_ref = 1737.4 / 6378.137
= 0.2723993 (the LOLA sphere), for both cones. They are not taken from the
Espenak pair: in profile mode the valleys come from the DEM, not from a
reduced k. That is a new `k` argument on the element computation, in both
languages.

The Moon's silhouette in the plane is r_M(ψ) = R_m · (1 + δρ(ψ)/1737.4).
Then, sampling the solar limb at angles φ:

- **Totality** (C2 → C3): the whole solar disk is inside the silhouette.
  With Q(φ) = P + R_s ê(φ),

      G_T(t) = max_φ [ |Q(φ)| − r_M(arg Q(φ)) ]      totality ⇔ G_T < 0

- **Annularity** (C2 → C3, antumbra): the whole silhouette is inside the
  solar disk. With M(ψ) = r_M(ψ) ê(ψ),

      G_A(t) = max_ψ [ |M(ψ) − P| − R_s ]             annularity ⇔ G_A < 0

For δρ ≡ 0 both reduce to today's `m − |L2'|` (|P| + R_s − R_m = m + L2' for
the umbra, R_m + |P| − R_s = m − L2' for the antumbra), to rounding plus the
φ-sampling bias R_s(1 − cos Δφ/2) ≈ 1e-7 R_s. That is the regression test.
The equation citation is [ES92] 8.33 for L1', L2' and m. The
silhouette-inclusion test is the geometric definition of the contacts
[NASA-limb], [Herald]. It is evaluated with the exact point Q rather than the
radial shortcut "solar limb at φ meets lunar limb at φ": the shortcut
evaluates δρ up to |P|/R_s ≈ |L2'|/L1' ≈ 1° away from the right angle near the
path edge, which is 20 bins of Δψ.

This is a parallel-ray, planar-silhouette model. Its only approximation is the
0.02° line-of-sight offset from §3.1. PR 2 checks it against an independent
brute-force 3D oracle (§5).

**Sampling φ.** δρ has structure at the 0.05° scale, so G_T samples the
solar limb at the profile's 7200 bin centres (Δφ = 0.05°) all the way round,
and G_A uses the bin centres directly. Their cos/sin come from libm, so the
two languages agree bit for bit. Bisection on t runs on top of that
(`circumstances._profile_contacts`).

### 3.4 Where it plugs in

| capability | today | profile mode |
| --- | --- | --- |
| `circumstances._local_raw` C2/C3, duration — **PR 2, done** | roots of `m − \|L2'\|` | G (G_T where L2' < 0, else G_A) sampled every 0.5 s over [C2 − 30 s, C3 + 30 s] of the mean limb, then bisection: first entry → C2, last exit → C3. An observer outside the mean umbra by < 12 km (the deepest valleys plus margin) is searched over ±3 min of maximum, because the profile can create or remove totality there (§9.7: two 2024 points outside the mean-limb path get 16–24 s). Profiles come from the 5-min lattice (`limb.profiles_at`, cached per node). |
| `shadow_edge_limits_v` umbral limits (envelope) | residual √s2 − \|L\| at the Newton-closest τ | residual min over τ of G(τ) around the closest-approach τ (±2 min, parabolic refinement). The limit is the *interior* limit, where totality just occurs. |
| `catalog._detail_raw` central duration, width | mean | profile, when requested |
| `circumstances_grid` (maps) | mean | last phase, gated on a performance budget (§6, PR 4) |
| magnitude, obscuration, C1/C4, penumbral limits | mean | unchanged (§7) |

**API.** A `limb=mean|profile` query parameter on `/circumstances` (PR 2,
done), then `/central-line`, `/map` and `/eclipses?detail=true`. Every
response echoes `"limb": ...`. An unknown value is a 400; missing limb
inputs are a 503. The default stays `mean`, the agreed default, because
every Espenak reference test is a mean-limb comparison and stays as it is.

**Native core.** A new pure-math `core/{include/eclipse,src}/limb.{hpp,cpp}`
covers the projection, binning, edge crossings, interpolation and, in PR 2,
G_T / G_A. `ephem::limb_axes` adds `pxform_c` to the CSPICE surface in
`ephem.cpp`, through `spice_call`.

The band follows the EOP table's pattern:
- Python parses the file (`kernels/limb_band.py`) and builds the pixel-centre
  trig tables and neighbour indices.
- It injects them once with `_eclipse.set_limb_band`, so the two languages
  project identical inputs.
- The C++ copy is read-only after that and lock-free, and the silhouette is
  OpenMP-parallel (per-thread maxima merged).

Operation order is mirrored: max-binning is order-independent, and the
projection, edge crossings and interpolation follow the Python left to right.
The Python side calls libm's `atan2` (`app.limb._atan2`), not `np.arctan2`,
whose SIMD kernel is 1 ulp off on ~7 % of inputs. So the parity is
bit-for-bit.

## 5. Validation

1. **Synthetic DEM (unit, both languages).** Use a sphere plus one
   spherical-cap mountain and one trench at known positions. ρ(ψ) matches the
   analytic silhouette. With δρ ≡ 0, G_T and G_A equal `m − |L2'|` (§3.3).
2. **Independent 3D oracle (test-only, Python).** For a handful of observers
   on the 2017 and 2024 central lines and within 2 km of the limits: cast rays
   from the observer to ~3600 points on the solar limb, and ray-march each
   against the DEM surface near the limb. This uses no fundamental-plane
   reduction and no profile binning. Target: C2/C3 agree with §3.3 to ≤ 0.05 s,
   and the limits to ≤ 50 m.
3. **Consistency with Espenak's `k2`.** `K_UMBRA` is 0.75 km below the LOLA
   sphere. So profile-mode central durations along 2017 and 2024 should agree
   with mean-limb durations *on average*, with a spread of ~1–3 s. Report the
   mean and spread. A mean offset larger than ~0.5 s would point at a
   reference-radius or frame bug.
4. **External limb-corrected values (the real gate).** A table of published
   LRO/Kaguya-based C2/C3 times for 6–10 sites across 2017-08-21 and
   2024-04-08: central-line, mid-path, and within 1 km of each limit.
   Candidates: X. Jubier's interactive maps (limb-corrected), Herald's
   *Occult*, and Espenak's per-eclipse predictions. Each value is stored with
   its provenance. Gate 0.3 s (the sources' ~0.2 s plus DEM differences).
   Failures are strict xfails with a note, never a wider gate.
5. **Parity.** The live checks are in `tests/test_native.py`:
   - PR 1: axes in four Earth frames × two Moon frames, silhouettes of a
     synthetic rough DEM and of the real band, `delta_rho_at`. All are
     bit-identical.
   - From PR 2: G, contacts, limits.

   The offline checks are in `tests/cpp/test_limb.cpp` against
   `limb_cases.txt`. The fixture carries a 1-pixel-per-degree synthetic
   band (runs, DN, neighbours, trig tables) with its silhouettes, so ctest
   needs no DEM. The `lax` axes rows need the lunar kernels and skip
   without them. A closed-form sphere test needs no fixture at all.

## 7. Out of scope (for now)

- **C1/C4 limb corrections.** Effects are ≲ 0.5 s and poorly observable, and
  they need a per-observer (topocentric) profile.
- **Magnitude and obscuration.** Changes are ~1e-3.
- **Penumbral limits.** No meaningful change.
- **The exterior graze-zone boundary** (Espenak's "60° unbroken crescent").
  This could be added later on top of G_T.
- **Solar-radius uncertainty and atmospheric refraction.** These are separate
  items. Refraction was on the earlier list.

## 8. Decisions

Settled:
- **Default after PR 4:** `limb=mean`, which stays comparable with the
  Espenak/NASA tables.
- **Restricted networks:** a pre-cut band plus the two lunar kernels are
  hosted on the `limb-data` branch (§2).

Open:
0. **Observer elevation — done** (§9.10). `geo_to_fund` takes the observer's
   height above the WGS-84 ellipsoid, exactly ([Meeus98] ch. 11, the
   geodetic normal rotated into the fundamental plane), in both languages;
   `/circumstances?elev=`. It explains Vale ([Irwin21]) but not Effingham
   ([EB2024], whose coordinates are too coarse there), and moves the
   mid-path median from 0.35 s to 0.30 s. `/map`, the limits and the catalog
   stay sea-level.
1. **`LDEM_64`?** PR 1's study (§9.1) crossed the 0.1 s threshold: C2/C3
   move 0.1–0.2 s typically and up to 0.5 s near the edge. The cost:
   - a ~200 MB band (16° cut), which has to be split across files for GitHub
     (100 MB per file);
   - ~12× the points per profile (~0.8 s native);
   - ~1.5 GB of neighbour indices in the current in-memory layout, so they
     would have to be computed on the fly.

   **Deferred to after PR 2** (agreed). Its 3D oracle validates the contact
   function these numbers come from, and the external gate (§5.4) is
   0.3 s, so we'll know then whether 0.1–0.5 s matters against the sources.
2. **External values (§5.4):** being found by web research (Claude). The
   sources and extracted values will be recorded, with provenance, before
   PR 4.

### 9.2 Grid edges

On a synthetic sphere seen straight along −x̂_ME, point binning alone gave
bins down to −18 km. The grid rows project to a comb of angles near the
equator, so some bins only see points from behind the limb. With grid edges
the sphere is flat to its 0.26 m sampling sag (`tests/test_limb.py`, and the
C++ closed-form test).

On the real 2024 profile, edges changed:

| | points only | points + edges |
| --- | --- | --- |
| adjacent-bin jumps, p99 / max (km) | 3.0 / 5.5 | 0.41 / 0.74 |
| mean δρ (km) | 0.46 | 0.61 |

### 9.4 Libration at eclipses

Over every eclipse from 1900 to 2100 (454, from `find_eclipses`), the view
axis ẑ was sampled every 10 min within ±4 h of greatest eclipse while the
axis was within 1.57 Earth radii of the Earth. Its angle from −x̂_ME never
exceeded **6.65°** (2089-04-11); p99 was 6.17°. The 20° band covers 12°.

### 9.5 Parity and speed

- **Parity:** Python and C++ agree bit for bit. With `np.arctan2` the
  residual was 4.5e-13 km on a real profile and 3.4e-12 km on a rough
  synthetic DEM. Steep edges amplify a 1-ulp angle difference through
  `frac = (bnd − ua)/du`, so the oracle uses libm's `atan2`.
- **Speed:** one profile takes 70 ms native (4 threads; 180 ms on one
  thread) and ~4 s in the Python oracle.

### 9.6 The 3D oracle, and the perspective fix

`tests/test_limb_oracle.py` is an independent ray tracer:

## 9 (cont.). Observer elevation

### 9.10 Height above the ellipsoid

**Formula.** A point at height H above the ellipsoid, along the geodetic
normal, has ρ sin φ′ = (b/a) sin u + (H/a) sin φ and ρ cos φ′ = cos u +
(H/a) cos φ ([Meeus98] ch. 11). So it is the ellipsoid point plus
H/a times the unit normal. The existing reduction ([ES92] eq. 8.331) is an
exact rotation of the ellipsoid point into the fundamental-plane axes. The
rotation is linear, so the height adds the rotated normal, in the spherical
form of [MeeusSE], as NASA's local-circumstances calculator does [NASA-LC]:

    ξ += (H/a) cos φ sin θ
    η += (H/a) (sin φ cos d − cos φ cos θ sin d)
    ζ += (H/a) (sin φ sin d + cos φ cos θ cos d)

This is exact, not a first-order term:
- `tests/test_geography.py` checks it against geodetic + H → ECEF → axes, to
  1.1e-15 Earth radii, up to H = 1000 km.
- The term is skipped at H = 0, so every sea-level result, fixture and
  reference test is bit-identical. The regenerated fixtures only *add*
  records.

**Grounding in the literature** (checked 2026-09-24):

| part of the approach | source | what it says |
| --- | --- | --- |
| ρ sin φ′, ρ cos φ′ with H | [Meeus98] ch. 11 ("Geocentric rectangular coordinates of an observer"; ch. 10, p. 78 in the 1991 1st ed., where the formulas are unnumbered) | `ρ sin φ′ = (b/a) sin u + (H/6378140) sin φ`, `ρ cos φ′ = cos u + (H/6378140) cos φ`, "needed in the calculation of diurnal parallaxes, eclipses and occultations" |
| the same, in production eclipse code | [NASA-LC] `SEcirc.js`, `readdata` (lines 399–401) | Meeus's formulas verbatim with the observer's altitude |
| ξ, η, ζ from ρ sin φ′, ρ cos φ′ | [NASA-LC] `timelocdependent` (lines 183–187); [MeeusSE] | ξ = ρcosφ′ sin h, η = ρsinφ′ cos d − ρcosφ′ cos h sin d, ζ = ρsinφ′ sin d + ρcosφ′ cos h cos d. Ours equals this to 4e-16 (WGS-84 constants), split so that H = 0 stays the [ES92] 8.331 reduction |
| elevation belongs in local circumstances | NASA/TP-1999-209484 (2001 bulletin), "Local Circumstances Tables" | sites are computed at their elevation "if known. Otherwise … for sea-level"; it matters "near the umbral path limits" |
| height = a ground shift of H cot(alt) | [NASA-limb] graze page ("Elev Fact"); IOTA's graze manual (x = sin D · tan z · h) | the sea-level limit moves perpendicular to itself by h · tan(90° − A) · sin D; our test checks the same equivalence in time (0.03 s at Vale) |
| h = H + N | NOAA NGS (Technical Notes on Geoid Undulations; NOS NGS 59); [EGM96] | ellipsoidal height = orthometric height + geoid undulation |

Meeus and NASA put the height "above sea level" directly into an ellipsoid
formula, which treats the geoid as the ellipsoid (−30 to −35 m of error
here). We add N [EGM96]. On the 14 test sites that changes the Bulletin
statistics by < 0.02 s (median 0.39 s either way; max 1.08 s with H alone,
1.10 s with H + N), so it is rigour, not a visible correction.

**What it is.** A raised observer sees what a sea-level one sees at the foot
of its line of sight to the Sun, H cot(alt) away from the Sun's azimuth.
`test_mean_limb_contacts_at_height_match_the_direct_3d_geometry` checks
that to 0.03 s at Vale (a 0.69 km shift). So a height moves C2/C3 by seconds
near a limit and by ~0.1–0.3 s mid-path, towards or away from the centre
line depending on the Sun's azimuth.

**Heights.** `elev` / `height_m` is above the **ellipsoid**. A map, SRTM or
GPS-with-geoid height H is above the geoid, so h = H + N [EGM96]. In the test
sites N is −30 to −35 m (Illinois/Indiana) and −17 m (Vale). SRTM90 [SRTM]
ground heights and EGM96 undulations, with provenance, are in
`docs/LIMB_VALIDATION_SOURCES.md`.

**Against [EB2024] (36 mid-path sites, 72 contacts).** The Bulletin has no

| model | sea level: median / p90 / max | at h = H + N |

| **profile** | 0.35 / 0.68 / 1.15 s | **0.30 / 0.61 / 1.10 s** |
